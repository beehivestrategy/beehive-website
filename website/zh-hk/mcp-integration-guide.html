綜合指南

完整版 MCP 整合指南

企業決策者需要了解的 Model Context Protocol（模型上下文協議）全部內容 — 從架構到部署。

核心要點

  1. MCP 是一項開放標準 由 Anthropic 於 2024 年 11 月提出，讓 AI 助手透過單一通用協議安全接入外部數據來源、工具與 API。
  2. 採用正在加速：SDK 月下載量超 9700 萬次、MCP 服務端超 10,000 個、GitHub 星標超 81,000 個（截至 2026 年；來源：Anthropic MCP 登錄檔與 GitHub 指標）。
  3. MCP 由三個元件構成：MCP 客戶端（AI 助手）、MCP 服務端（數據聯結器）與 MCP 協議（JSON-RPC 2.0 通訊層）。
  4. 企業級部署需 2–8週，而傳統 BI 整合需要 6–12 個月（來源：Beehive Strategy 部署數據，2026 年）。
  5. MCP 不繫結廠商：它可與 Claude、GPT、DeepSeek、Qwen 以及任何實現客戶端規範的 LLM 協同工作。
第 1 節 · 定義

甚麼是 MCP？

面向企業決策者與架構師的 Model Context Protocol（模型上下文協議）權威解讀。

Model Context Protocol（MCP，模型上下文協議，一種讓 AI 安全接入企業數據的開放標準）由 Anthropic 於 2024 年 11 月推出，它使 AI 助手能夠透過一套通用協議安全接入外部數據來源、工具與 API。 它取代了過去點對點整合的碎片化格局 — 即每個 AI 模型都要為每個數據來源單獨訂造聯結器 — 代之以單一的標準化通訊層，任何 AI 助手都能借此動態發現並呼叫工具。

在 MCP 出現之前，要把 AI 助手接入企業數據來源，必須為每套系統單獨開發整合：處理認證、轉換查詢、格式化響應、管理錯誤。一家擁有 10 個數據來源和 3 個 AI 模型的公司，最多需要 30 套獨立整合。MCP 把這種複雜性收斂為一套協議，使任何相容 MCP 的客戶端都能與任何相容 MCP 的服務端通訊，無需訂造粘合程式碼。

“MCP 是一項開放協議，它規範了應用向 LLM 提供上下文的方式。可以把 MCP 理解為 AI 應用的 USB-C 介面：它為 AI 模型連線不同的數據來源與工具提供了統一方式。”

— Anthropic，MCP 規範（modelcontextprotocol.io）

MCP 發展簡史

Anthropic 於 2024 年 11 月 25 日以 MIT 許可的開源項目形式釋出了 Model Context Protocol 規範。其目標是解決 LLM 能力足以作用於企業數據後出現的一個問題：每一套整合都是訂造的、脆弱的，並且鎖定在特定模型上。不到半年，該協議已被 Cursor、Windsurf、Zed 等主流開發工具採用，並出現了面向數據庫、SaaS 平臺與開發者工具的服務端實現。到 2026 年，MCP 已成為 AI 連線數據的事實標準，活躍的社群每週都在貢獻新的服務端與客戶端庫。

第 2 節 · 技術

MCP 如何工作

配套每一次 MCP 連線的三元件架構與 JSON-RPC 2.0 協議。

MCP 透過三個元件之間的清晰職責劃分來運作。理解這三個角色，對任何規劃企業級 MCP 部署的人都至關重要。

MCP 客戶端

發起請求的 AI 助手或應用。客戶端通常內嵌在由 LLM 驅動的工具中，例如 Claude Desktop、Cursor 或企業 AI 代理平臺。客戶端先發現可用的工具與資源，再按需呼叫它們來回答使用者提問。

MCP 服務端

透過 MCP 協議暴露某個數據來源或工具的輕量程式。服務端對外宣告自身能力 — 工具、資源與提示詞 — 並處理來自任何 MCP 客戶端的請求。一個服務端可以封裝一個 PostgreSQL 數據庫、一個 Slack 工作區，或一套訂造的內部 API。

MCP 協議

客戶端與服務端之間的通訊層。該協議基於 JSON-RPC 2.0 構建，定義了用於能力發現、工具呼叫、資源讀取與提示詞管理的標準方法集。傳輸方式包括 stdio（本地）與 HTTP + SSE（遠端）。

JSON-RPC 2.0 傳輸

每條 MCP 訊息都是一個 JSON-RPC 2.0 物件。這一設計選擇有三方面意義：無狀態、與程式語言無關，且大多數後端開發者已經熟悉。客戶端傳送帶有方法名與引數的請求物件；服務端返回帶有結果或錯誤的響應物件。同時還支援通知（單向訊息），用於流式返回與進度更新。

協議定義了服務端可暴露的四類原語：

  1. 工具 — AI 可呼叫的可執行函式，例如 run_sql_query 或 send_slack_message。工具帶有型別化的輸入結構，並返回結構化結果。
  2. 資源 — AI 可讀取的數據，例如數據庫表結構、配置檔案或日誌流。資源透過 URI 標識。
  3. 提示詞 — 預定義的模板，用於引導 AI 在特定任務中的行為，例如帶引數化輸入的「summarise this table」提示詞。
  4. 發現 — 客戶端透過握手瞭解服務端提供哪些工具、資源與提示詞，無需事先硬編碼任何內容。

MCP 服務端基礎示例

以下 Python 程式碼片段展示瞭如何構建一個僅暴露單個工具的極簡 MCP 服務端。示例使用 Anthropic 官方 MCP Python SDK：

    Args:
        region: 銷售區域（例如 'east'、'west'、'north'）
        quarter: 財季（例如 'Q1'、'Q2'、'Q3'、'Q4'）
    """
    # 在生產環境中，此處會透過語意層查詢數據倉儲
    # 並應用 RBAC 許可權控制
    return {
        "region": region,
        "quarter": quarter,
        "total_revenue": 1_245_000,
        "currency": "CNY",
        "source": "semantic_layer.v2"

# 透過 stdio 傳輸方式啟動服務端
if __name__ == "__main__":

該服務端註冊到 MCP 客戶端後，任何已連線的 AI 助手都能發現 get_revenue_by_region 工具，並在使用者提出營收相關問題時呼叫它 — 客戶端無需任何訂造整合程式碼。

第 3 節 · 架構

MCP 架構分層

企業級 MCP 部署如何以四層結構交付受管治的對話式智慧。

生產級 MCP 部署遠不止一個服務端。企業通常會實施四層疊加架構，每層解決一類不同的問題。正是這種分層架構，把玩具級演示與能夠透過安全審計、服務數千名使用者的正式部署區分開來。

第 1 層

數據連線層

基礎層。MCP 服務端封裝各個數據來源 — MySQL、PostgreSQL、Snowflake、BigQuery、Salesforce、SAP、REST API — 並透過標準協議對外暴露。該層負責認證、連線池、查詢執行與結果格式化。在 Beehive Strategy 的部署中，該層包含 50+ 個預置聯結器以及一套訂造聯結器開發框架。

第 2 層

語意層（受管治的指標）

位於連線層之上，把業務術語對映到技術數據結構。當使用者問「上季度各區域的毛利率是多少？」，語意層知道需要哪些表、哪些欄位、哪些關聯與計算 — 並執行行級安全與指標定義等管治規則。正是這一層讓 MCP 的答案可信：每個指標都有唯一且受管治的定義。

第 3 層

AI 代理層

由 LLM 驅動的代理接收自然語言提問，藉助語意層判斷需要哪些數據，呼叫 MCP 工具取數，並以自然語言配合自動生成的圖表返回結果。代理可以按領域劃分（銷售、財務、供應鏈），並組合成多代理工作流以處理複雜任務。

第 4 層

安全 & 管治層

橫跨各層的切面層，負責認證（OAuth 2.0）、授權（RBAC）、審計日誌、個人資訊脫敏，以及 PIPL、GDPR 等法規的合規。每一層的每一次請求都要經過這一管治封裝，確保訪問始終經過認證、授權且可追溯。

第 4 節 · 對比

MCP 與 REST API、GraphQL 及訂造整合在企業 AI 所關注的關鍵維度上的對比。

MCP 並不是把 AI 助手接入數據的唯一方式，但它是唯一專為 AI 使用而設計的方式。下表按企業架構師選擇整合策略時評估的維度，將 MCP 與三種最常見的替代方案進行比較。

第 5 節 · 部署

企業級 MCP 部署步驟

把 MCP 從評估推向生產的五步框架。

在企業環境中部署 MCP，與在本地跑一個演示服務端有本質區別。以下五步框架基於 Beehive Strategy 的部署方法論，並在零售、金融、製造與專業服務領域的數十個企業項目中打磨完善。

1

盤點數據來源與使用情境

首先梳理團隊查詢最頻繁的數據來源，以及目前耗時最久才能回答的業務問題。為首期部署優先挑選 3–5 個高價值數據來源。常見的起點包括主數據倉儲、CRM 與 ERP 系統。把具體使用情境 — 「銷售管道健康度」「各區域庫存週轉率」「月度現金消耗」 — 記錄下來，它們將定義項目的成功標準。

2

設計語意層與管治規則

在接入任何 AI 之前，先定義受管治的指標字典。在貴司，「營收」指甚麼 — 已簽約、已確認還是已回款？誰有權檢視薪酬數據？語意層把這些定義與許可權固化下來，使每個 AI 答案都一致、受管治且可審計。這一步通常需要 1–2週，是決定系統長期可信度的首要因素。

3

構建並部署 MCP 服務端

為標準數據來源（MySQL、Snowflake、Salesforce）部署預置 MCP 服務端，併為自有系統開發訂造服務端。每個服務端將其工具、資源與提示詞註冊到 MCP 閘道器，由閘道器統一處理認證、路由與日誌。在 Beehive Strategy 的部署中，該步驟依託 50+ 個預置聯結器，首期數據來源通常 3–5 天即可完成。

4

接入 AI 代理並測試

將一個或多個 AI 代理接入 MCP 閘道器，並開展結構化測試。測試需覆蓋準確性（代理返回的數字是否正確？）、管治（是否遵守 RBAC 邊界？）與效能（響應延遲是否可接受？）。同時驗證語意層在面對同一問題的不同問法時，能否給出一致的答案。

5

投入運作生產並配套監控

透過團隊已在使用的即時通訊工具 — 釘釘、飛書或 Microsoft Teams，向真實使用者開放。對每一次提問、每一次工具呼叫、每一次響應都埋點監控。建立查詢量、延遲、錯誤率與使用者採用度的儀表板。建立回饋循環，使語意層缺口與代理錯誤能在數天內被發現並修正，而不是拖上數月。

第 6 節 · 安全

MCP 安全 & 合規

讓 MCP 能夠安全承載企業數據的安全控制 — 從認證到審計。

安全是企業在評估 MCP 時最常提出的顧慮。協議本身在設計時已考慮安全，但生產級安全取決於 MCP 閘道器的具體實現。以下四項控制對任何企業級部署都是不可或缺的。

OAuth 2.0 認證

MCP 以 OAuth 2.0 為主要認證機制。每次客戶端連線都需要有效令牌，且令牌的作用範圍限定在特定服務端與操作上。這意味著，一個被授權查詢銷售數據庫的使用者，不會自動獲得 HR 數據的訪問許可權。企業級部署應將 OAuth 與既有身份提供商（Okta、Azure AD 或國內身份服務商）對接，實現單點登入。

RBAC 與許可權範圍控制

基於角色的存取控制確保使用者只能看到其被授權訪問的數據。語意層在查詢時執行行級與列級許可權 — 區域經理只能看到本區域的數據，即使他與全球高管提出的是同一個問題。許可權在管治層一次性定義，並在每一次 AI 互動中一致執行。

PIPL 與 GDPR 合規

對於在中國內地或歐盟營運的機構，數據隱私法規不是可選項。MCP 部署必須支援在語意層進行個人資訊脫敏、數據駐留控制（把數據限定在特定司法轄區內）以及同意管理。Beehive Strategy 的 MCP 閘道器在設計上符合中國《個人資訊保護法》（PIPL）與歐盟 GDPR 的要求，對敏感工作負載還可選擇本地化或私有云部署。

審計追蹤與日誌

每一次提問、每一次工具呼叫、每一次數據訪問、每一次配置變更，都會連同完整上下文被記錄：誰問的、問了甚麼、呼叫了哪些工具、返回了哪些數據、發生在何時。這些審計軌跡既滿足合規要求，也為事件調查提供取證數據。日誌具備防篡改特性，並可流式接入 SIEM 系統以實現實時告警。

MCP 常見應用情境

企業中投資回報最高的四類 MCP 應用。

MCP 是一種通用協議，但在實踐中，企業部署的情境高度集中在以下四類。這些應用中，自然語言取數、受管治的指標與即時通訊原生交付三者結合，帶來的投資回報最為清晰。

對話式 BI

旗艦情境。高管與一線管理者用自然語言提出數據問題 — 「為甚麼第三季度東區營收下滑？」 — 並即時獲得帶自動生成圖表的答案，結果直接推送到釘釘或飛書等即時通訊工具中。無需寫 SQL，無需儀表板，也無需等待數據團隊。

自動化報表

用按計劃執行的 AI 代理取代手工報表製作：代理透過 MCP 取數、套用語意層的受管治定義，並按計劃把格式化報表投遞到指定渠道。月度結賬包、每週銷售摘要、每日營運儀表板都可以自動生成。

跨系統數據查詢

MCP 的多服務端架構讓單個 AI 代理能在一次對話中查詢多套系統。使用者可以問「把 CRM 中過去 90 天未在 ERP 下單的客戶找出來」 — 代理會編排跨兩個服務端的呼叫，並透過語意層完成結果關聯。

AI 代理工作流

多步驟業務流程 — 例如「分析本月供應連結串列現，找出前三大瓶頸，並起草一份整改備忘錄」 — 可以編碼為代理工作流，把多次 MCP 工具呼叫串聯起來。這些工作流自主執行，並把成品交付給相關干係人。

常見問題

關於模型上下文協議最常見問題的直接解答。

甚麼是 MCP？

模型上下文協議（MCP）是 Anthropic 於 2024 年 11 月推出的一項開放標準，它使 AI 助手能夠透過一套通用協議安全接入外部數據來源、工具與 API。它以基於 JSON-RPC 2.0 的單一標準化通訊層，取代了碎片化的點對點整合。任何相容 MCP 的客戶端都能發現並呼叫任何相容 MCP 的服務端上的工具，無需訂造整合程式碼。

MCP 如何工作？

MCP 由三個元件構成：MCP 客戶端（內嵌於 AI 助手）、MCP 服務端（連線數據來源或工具的輕量聯結器）以及 MCP 協議（JSON-RPC 2.0 通訊層）。客戶端先從服務端發現可用的工具、資源與提示詞，再按需呼叫它們來回答使用者提問。傳輸方式包括用於本地連線的 stdio，以及用於遠端連線的 HTTP 與 Server-Sent Events。

MCP 安全嗎？

安全。MCP 支援 OAuth 2.0 認證、基於角色的存取控制（RBAC）、許可權範圍控制與完整審計日誌。透過 Beehive Strategy 這類企業級 MCP 閘道器部署時，可滿足 PIPL、GDPR 與 ISO 27001 的要求。所有數據傳輸均加密，訪問在資源級別受管治，每一次查詢都會留痕以供審計與合規之用。

MCP 部署需要多長時間？

包含 3 個數據來源的 Quick Start 部署可在 2星期內投入運作。包含 10 個以上數據來源、訂造語意模型與多代理工作流的完整專業版部署，通常需要 6–8週。部署週期主要取決於需要接入的數據來源數量，以及管治與語意層需求的複雜程度。

MCP 支援哪些數據來源？

只要某個數據來源有對應的聯結器，MCP 就能支援。常見的數據來源包括 MySQL、PostgreSQL、SQL Server、Oracle、Snowflake、BigQuery、Redshift、Salesforce、SAP、HubSpot、Slack、GitHub、Notion，以及釘釘、飛書、支付寶等中國本土企業工具。對於自有或訂造系統，使用官方 SDK 幾天即可開發一個新的 MCP 服務端。

MCP 與 API 有何不同？

傳統 API（REST、GraphQL）對每個數據來源都需要訂造整合程式碼，且並非為 AI 使用而設計 — 必須顯式教 AI 模型如何呼叫每個端點。MCP 提供一套通用協議，任何 AI 助手都能借此動態發現並呼叫工具，無需按數據來源做整合工作。這意味著新數據來源對所有已接入的 AI 模型立即可用，更換 AI 模型也不需要重構數據管道。

MCP 能與現有 BI 工具配合使用嗎？

可以。MCP 的語意層本身就是一個受管治的指標層，Tableau、Power BI、Metabase 等現有 BI 工具可以與對話式介面一起查詢它。團隊可以繼續使用既有儀表板，同時透過即時通訊工具中的自然語言對話訪問同一套受管治指標。這種雙通道模式既保護了既有投入，又把數據訪問許可權擴充套件到了非技術使用者。
